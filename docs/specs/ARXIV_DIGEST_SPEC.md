# arXiv 跟踪摘报(功能规划第三批,收尾项)

- 日期: 2026-07-20
- 范围: `arxiv_digest` 工具
- 实现位置: fork 的 `packages/scholar/src/arxiv/digest.ts`

## 设计取舍:主题必须显式给出

这是当初规划里明确标注"优先级最低、可能做成 skill 而非核心工具"的一项,实现时保留了这个审慎——但审慎不体现在"要不要做",而体现在"怎么做"上。最容易做错的方式是从 `RESEARCH.md` 自动抽取关键词(简单的词频/去停用词启发式),图省事但精度靠不住:研究问题的表述往往是自然语言句子,机械抽词容易抽出不代表真实检索意图的词,查回来的结果噪音大,长期会让用户不信任这个功能。

所以工具描述里直接要求调用方(agent)自己先读 `RESEARCH.md`,理解研究问题,再总结成精确的检索主题传进来——本质是把"理解意图"这一步留给模型做(它擅长),把"我们不擅长做好的启发式"这一步删掉。这与项目里其他地方的一贯选择一致(比如 `paper_note`/`experiment_log` 都要求显式结构化字段而不是让工具自己猜)。

## 接口与行为

`arxiv_digest(topics)`:`topics` 是一个数组,每项是 `{topic, maxResults?}`,支持多主题一次查询。查询按 arXiv 提交时间倒序(`sortBy=submittedDate&sortOrder=descending`),这是刻意选择——目的是"发现新论文",不是"找相关论文"(那是 `scholar_search` 的活),按相关性排序会让老论文持续出现,失去跟踪意义。

去重排除逻辑:项目 `.research/notes/` 里任何一篇笔记对应的论文(不论阅读状态,`to_read`/`reading`/`read` 都算"已知"),按 arXiv id 精确匹配或标题模糊匹配双重判据排除,避免因为某篇论文的笔记记录里缺 arXiv id(比如手动创建的笔记)而漏判成"新论文"反复出现。排除数量如实报告在返回结果里,不是静默丢弃。多主题都命中的论文排在结果前面(更可能真正相关),同等命中数按提交时间新旧排序。

## 实现上的一个测试性设计

去重/排序/排除这套核心逻辑(`mergeDigestHits`)被拆成一个不碰网络、不碰磁盘的纯函数,输入是"每个主题各自查到的命中列表"加一个"是否已跟踪"的判定函数,输出是最终结果。这让排序规则(多主题优先、其次按新旧、已跟踪的要计数不能丢)可以用合成数据直接单元测试,不必每条规则都靠真实网络请求验证——网络层(`fetchRecentByTopic`)和数据库层(`alreadyTrackedMatcher`)各自独立、各自可单独测试或替换。

## 未做

真正的"定期"执行——这个工具本身是按需调用的,不含调度能力;要做成"每天自动跑一次发我摘要"需要接上宿主的后台任务或外部 cron,这一步留给用户自己配置(或者未来看是否值得包成一个 skill)。跨语言/跨来源(比如 bioRxiv、Semantic Scholar 的新论文提醒)——目前只查 arXiv,其余学科的用户覆盖不到。
