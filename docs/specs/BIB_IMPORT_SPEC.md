# BibTeX/Zotero 批量导入(功能规划第三批)

- 日期: 2026-07-20
- 范围: `bib_import` 工具,把用户存量的 BibTeX 库一次性迁入项目
- 实现位置: fork 的 `packages/scholar/src/cite/import.ts`

## 为什么这是发布前最重要的一项

前两批做的都是"从零开始积累"的能力——搜、下、读、写、审,全部假设用户是从空的 `.research/` 目录起步。但真实的研究者从来不是从零起步:他们手上已经有几十到几百篇论文躺在 Zotero 或 EndNote 里。如果新用户第一次打开 Scholar CLI 时,面对的是"请对着你已经读过的论文重新一篇篇 search+download",拉新门槛会高到不合理。`bib_import` 让存量库五分钟内可用,这是产品愿景里"通用 coding agent 帮你写代码,我们陪你做完一项研究"这句话对老研究者同样成立的前提。

## 设计取舍

**BibTeX 解析器手写、零依赖。** 与 `packages/scholar` 一贯的"只用 node 内建,不引入依赖"的立场一致(参见包 README)。解析器用平衡括号扫描取字段值(应付跨行、嵌套一层花括号如 `{A Study of {GPT}}` 的情况),同时支持 `{...}`、`"..."`、裸 token 三种取值写法,`author` 字段按 `Last, First` 和 `First Last` 两种常见形式统一转成后者,`eprint` + `archivePrefix: arXiv` 或形如 `\d{4}\.\d{4,5}` 的 eprint 值被识别为 arXiv id。

**笔记状态统一从 `to_read` 起步,绝不冒充"已读"。** 用户实际读没读过导入的这几百篇论文,我们无从得知;精读笔记的核心价值(结构化理解、与项目问题的关联)也不是导入能凭空生成的。所以导入只建占位笔记,真正的精读仍要靠 reader 子 agent 后续补上——这也是为什么 checker/synthesizer 只信任精读笔记而不信任"存在一条 to_read 记录"这件事本身。

**BibTeX 条目原样保留原 key,不重新生成。** 这是刻意的兼容性决定:用户很可能带着一份已经在写的、`\cite{某个旧 key}` 到处都是的稿件来迁移,如果导入时按 `paper_cite` 的规则重新生成 key,稿件里的引用全部失效。原样保留意味着迁移后旧稿件立刻能编译。新建的引用(通过 `paper_cite`)仍然走原来的 `姓+年份+标题词` 规则,两套 key 风格在同一个 `references.bib` 里共存是可接受的——bib 文件本来就不要求 key 风格统一。

**幂等,可安全重复执行。** 已经被追踪的论文(不论 paperId 来自 doi、arXiv id 还是合成的 `bibkey-` 前缀)不会被覆盖笔记状态——如果用户在两次导入之间已经通过 reader 精读了某篇论文,第二次导入不会把它打回 `to_read`。重复的 bib key 直接跳过,不产生重复条目。

**下载默认关闭,失败不阻断整批。** 参照归档 ADR-004 批量成本确认的精神,但落地方式不同:ADR-004 设想的是一个交互式确认对话框,而工具调用没有这种原语,所以选择更保守的默认值(`download: false`)加上工具描述里的明确提示——"导入大库开着下载意味着很多次下载,超过几篇之前先问用户"。开着下载时,每条目独立 try/catch,某几篇下载失败(网络问题、非开放获取)不会让整批导入失败,失败原因逐条汇报。

## 接口

`bib_import(source, download?)`:`source` 接受 worktree 内的相对路径(指向 `.bib` 文件)或直接传入原始 BibTeX 文本(靠是否包含 `@` 且不以 `.bib` 结尾粗略判断,工具层用路径拼接兜底)。返回值统计新建笔记数、已存在跳过数、bib 追加数、下载成功/失败数,失败明细逐条列出。
