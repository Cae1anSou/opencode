# Claude Code 编排层:可移植设计模式清单

- 日期: 2026-07-19
- 参考源码: 分析时读的是 Claude Code 的 sourcemap 反解产物(非开源许可,本地临时材料,从未也不会进入任何仓库——本文档记录的设计结论是唯一保留的产物,原始反解源码不随本次仓库合并迁移)
- 法律边界: **只移植设计,不移植代码。** 本仓库及公开产品中不得出现从该参考源码复制的任何代码片段。本文档记录的是架构模式与类型契约的设计思想,实现必须由我们自己重写。
- 配套阅读: `opencode-core-analysis.md`(宿主现状)、`codex-core-analysis.md`(另一种实现路线的对照)

## 移植的总体思路

OpenCode 的分工是:自己管会话状态机与 prompt 组装,把工具调用运行时交给 AI SDK 的 `streamText()`。这个分工对二开者友好,但也意味着工具调度、权限、压缩这些编排能力受 AI SDK 的抽象限制。我们的策略是把循环所有权收回:保留 AI SDK 作为模型 I/O 客户端(多 provider 兼容、流式解析),但在它之上自建 agent 循环,循环内的工具调度、权限管线、上下文压缩、子任务模型参考 Claude Code 的设计重新实现。

Claude Code 的核心循环(其 `query.ts` 中的 queryLoop)结构值得作为蓝本:一个 `while(true)` 循环,每轮先做上下文压缩决策,再流式消费模型输出、累积工具调用块,流结束后若无后续需求则完成,否则执行工具、把结果拼回消息、写回状态进入下一轮。Claude Code 用 async generator 贯穿全链路;在我们这里(ADR-018 采纳 Effect 后),同样的结构以 Effect 服务实现——`Effect.gen` 生成器表达循环,fiber 承载并发与中断,流式事件走 Effect 的流原语。上游 v1.18.x 的 `SessionPrompt.runLoop` 本身已是这个形态,我们是在它的骨架上替换与增强,而非另起炉灶。

## 值得移植的模式,按优先级排列

### 一、Tool 类型契约与声明式并发安全

Claude Code 的 Tool 接口在输入 schema(zod)之外,让每个工具声明自身性质:是否只读、是否并发安全、如何校验输入、如何检查权限、如何渲染进度。关键巧思是 fail-closed 默认值——工具未声明 `isConcurrencySafe` 时默认按不安全处理。调度层据此把连续的只读/并发安全工具自动分批并行(有并发上限),不安全工具串行执行。这让"哪些工具能并行"成为工具自己的声明,而不是调度器里的硬编码清单。对我们的意义:精读 SubAgent、文献搜索这类只读工具可安全并行,写记忆、写稿件的工具自动串行,恰好落实归档 ADR-006 的串行化原则。

### 二、工具执行管线:校验 → 权限 → 钩子 → 执行 → 钩子

单次工具调用不是一个函数调用,而是一条固定管线:schema 校验、业务校验、PreToolUse 钩子、权限决策(allow/ask/deny)、执行、PostToolUse 钩子,每步都有遥测点。权限与钩子内嵌在执行路径里而非旁路,保证任何工具调用都无法绕过。对我们的意义:成本确认(归档 ADR-004)、危险操作拦截、实验运行前的确认,都作为钩子挂进这条管线,不散落在各工具内部。

### 三、多策略上下文压缩体系

Claude Code 不是单一 autocompact,而是多种策略并存、按特性开关灰度:常规自动压缩、历史裁剪、缓存友好的微压缩、可折叠上下文视图、事后补救式压缩。对我们的意义:科研会话的上下文有明确的领域结构(论文笔记、实验摘要、稿件状态),压缩不必只靠"让模型总结历史"——领域对象可以整块换出(卸载某篇论文的笔记,保留一行索引),需要时再换入。先实现两档:领域对象换入换出(利用记忆图谱,优先)与兜底 autocompact(通用),后续按需加细。

### 四、SubAgent / Task 模型

子 agent 通过递归调用同一个查询入口实现,天然支持嵌套;每个子 agent 独立上下文窗口(即归档 ADR-003 的 token 池隔离),返回结构化结果而非对话文本。对我们的意义:精读 SubAgent 是第一个用户;它的输入是全文与项目问题,输出是结构化笔记(schema 见后续设计),与主会话完全隔离。Claude Code 更进一步的 coordinator/teammate 多 agent 协作模式暂不移植,等到"多篇论文并行精读 + 汇总对比"成为瓶颈时再评估。

### 五、值得对照 codex-rs 的两处(ADR-018 后改判)

取消传播与重试收敛原计划参照 codex 手工实现(CancellationToken 派生 + abort-on-drop;重试逻辑单一入口)。ADR-018 采纳 Effect 后,这两项由框架原语直接承担:fiber 的层级化中断即取消传播,Scope 即资源安全,Schedule 即重试策略。移植任务从"手工实现"改判为"正确使用框架"——但 codex 的两条设计纪律仍然有效:取消必须从 turn 级穿透到每个工具与 SubAgent,不允许出现不可中断的悬挂任务;重试策略必须收敛在模型客户端封装层的单一入口,不在各处复制粘贴。

## 不移植的东西

操作系统级沙箱(codex 的 landlock/bwrap 路线):科研场景的风险面主要是成本与数据覆盖,不是任意代码执行,权限管线 + 确认钩子够用,不为此引入平台相关复杂度。Claude Code 的插件市场与企业治理体系:公开产品早期不需要。UI 层的一切:参考源码中的 UI 文件是反解噪音重灾区,无参考价值。

## 落地顺序

第一步,在 fork 后的宿主里先不改 OpenCode 原循环,以 Effect 服务形态把现有 tools(搜索/下载/fulltext)注册进宿主工具系统跑通;新版架构分析已完成(`opencode-core-analysis-v2.md`),其结论是上游已实现执行管线的大半(校验-钩子-截断-遥测-权限),我们的自研增量收敛为并发安全分区调度、领域对象换入换出、记忆图谱三块,循环本体以"增强"替代原计划的"替换"。第二步,按本文的 Tool 契约与执行管线设计,在宿主的 ToolRegistry/Permission 机制上做增强或替换,迁移现有工具到新契约。第三步,实现领域对象换入换出的上下文管理,接通记忆底座。第四步,精读 SubAgent 作为 Task 模型的第一个实例落地(宿主已有 task.ts 子任务机制,优先评估复用)。每步都保持宿主原功能可用(归档 ADR-014 的回归测试原则)。
