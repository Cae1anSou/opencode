# Scholar CLI 产品愿景 v2

- 日期: 2026-07-19
- 状态: 现行有效,取代 `docs/archive/PRD_v1.md` 中的定位与范围章节
- 决策基线: 本文档 + `docs/product/ADR_DISPOSITION.md`

## 一句话定位

通用 coding agent 帮你写代码,Scholar CLI 陪你做完一项研究——从读透关键论文,到跑通实验,到写出经得起审稿的稿子,全程记得你读过什么、想过什么、试过什么。

## 我们要解决的问题

科研工作者的困境不是"找不到文献",而是一个活跃研究项目横跨数月,其间的理解、争论、实验和写作分散在文献管理器、聊天记录、实验脚本和草稿文件里,彼此断裂。每次打开一个新的 AI 对话,过去积累的理解都归零;每次写 related work,都要重新翻一遍读过的论文;每次审视实验结果,都要靠人脑回忆它对应稿子里的哪个主张。

市面上的"AI + 文献"工具(Zotero 问答插件、各类 RAG 检索器)解决的是静态文献库的检索问题:我有一千篇论文,帮我找到相关的几篇。Scholar CLI 解决的是另一个问题——理解与延续的问题:我正盯着这五到二十篇核心论文,帮我做出经得起审稿的深度综合判断,并且把这个过程中的一切积累下来,让三周后的我能无缝接上。

这也是我们与"用户自己在 Claude Code / Codex 上配几个 MCP"的本质区别。通用 harness 的记忆是代码库取向的,没有"论文—笔记—实验—稿件"这套领域对象模型。用户能白嫖到零散的搜索和总结功能,但复现不了一套贯穿整个研究项目生命周期的状态。

## 中心对象:研究项目

产品的中心对象不是文献库,而是研究项目。一个项目里有四类一等公民对象,它们互相引用、共享一份长期记忆:

正在精读的论文(全文、结构化笔记、阅读状态、历次讨论);积累的理解(项目的研究问题、假设、争论点、阶段结论);正在跑的实验(每次 run 的假设、配置、结果,以及它验证或推翻了什么);正在写的稿件(LaTeX 源、每个 claim 的依据链、引用库)。

这四者之间的关联图——哪篇论文的哪个方法启发了哪次实验,哪次实验的结果支撑了稿件里的哪张表,哪条 citation 背后有哪份精读笔记作证——就是产品的底座,我们称之为项目记忆图谱。RESEARCH.md 只是它的人类可读投影,不是它本身。

## 三根支柱

### 支柱一:精读与长期跟踪

论文进入项目后,由精读 SubAgent 完成深度阅读:不是"总结一下",而是逐节读透、提取方法与实验设置,并主动关联到项目的研究问题("这篇的方法对我们的问题意味着什么")。全文获取优先走 LaTeX 源(已实现的 fulltext resolver:LaTeX → HTML → OA PDF → OCR 四级回退),保证精读建立在干净文本之上。

长期跟踪的含义是:每篇论文的理解和历次讨论都被持久化。三周后用户说"接着上次对那篇 XX 的讨论",agent 能接得上。跨论文的方法对比、争议点梳理,基于的是这些精读笔记,而不是原文的向量碎片——要求整体理解的任务(对比五篇论文的实验方法、梳理领域内的方法论分歧),chunk 级检索天然做不好,这正是精读路线的阵地。

### 支柱二:写作与引用

稿件就在项目仓库里,用 LaTeX 加 Git 管理。写作时 agent 从用户自己的精读笔记里找依据和引文,而不是临时去搜——每条引用都对应真正读过、有笔记支撑的论文,BibTeX 自动维护。在此之上是审稿人视角检查:每个 claim 有没有 citation 支撑、被引论文是否真的说了那句话(笔记可查证)。Related work 的起草因此可信:它写的是消化过的内容,不是检索拼贴。

### 支柱三:实验与代码

这是 fork 成熟 harness 的最大红利——写代码、跑脚本、管 Git 是宿主的本职能力。我们添加的是领域层:实验记录的结构化 schema(每次实验对应什么假设、配置、结果),实验结果与稿件 claim 的关联(论文里那张表对应哪次 run),以及"从精读笔记的方法节生成复现计划"这类把支柱一与支柱三串联的能力。

## 底座:项目记忆与上下文管理

上下文管理策略从记忆图谱派生:当前对话按需加载相关论文的笔记(而非全文)、相关实验的摘要、稿件的当前状态。向量检索保留为底座里的一个粗筛手段,只在"从数百篇里捞相关"的场景启用,不再是核心架构(见 ADR_DISPOSITION 对 ADR-016/017 的处置)。

## 技术路线

宿主选择 fork OpenCode(MIT、TypeScript)。理由从当前需求倒推:三根支柱都需要大量领域工具与记忆结构,已有的 `packages/tools` 与学术生态的可用轮子(citation-js、pdf 解析、arXiv 客户端)几乎全在 npm;OpenCode 把工具调用运行时交给 AI SDK、自己只管会话状态机与 prompt 组装,我们要改造的恰恰是它自管的那层;MIT 许可对公开产品最干净。

编排层的改进策略是"移植设计而非代码":保留 AI SDK 作为模型 I/O 客户端,但把 agent 循环的所有权收回到自己手里,参考 Claude Code 的编排设计重新实现(详见 `docs/architecture/claude-code-orchestration-portable-patterns.md`)。上游自 2026-03-30 起已将编排层全面重写为 Effect-ts 风格,我们决定跟随最新版并采纳 Effect 作为编排层实现基底——其 fiber 并发、取消传播与重试原语恰好覆盖了原计划从 codex-rs 手工移植的能力(决策记录见 `docs/adr/ADR-018-fork-base-and-effect.md`);领域逻辑保持朴素 TS,将框架侵入面控制在编排边界。codex-rs 与 claude-code 的源码保存在 `references/` 下,仅作设计参考;claude-code 为 sourcemap 反解产物且非开源许可,严禁将其代码复制进本仓库或公开产品。

## 路线图

按支柱的依赖关系推进。第一阶段,fork OpenCode 并跑通宿主,把现有 tools(搜索、下载、fulltext)注册为内置工具,达到"能在 CLI 里搜、下、读全文"。第二阶段,集中建设精读子系统与记忆底座——这是三根支柱共同依赖的核心,也是差异化所在。第三阶段做写作子系统,它消费精读笔记。第四阶段做实验子系统,它复用宿主已有的 coding 能力,增量最小。测试与文档贯穿各阶段,质量门禁沿用原计划(覆盖率 > 80%,核心流程稳定)。

## 成功判据

一个真实的研究项目(例如一篇方法改进型论文)能在 Scholar CLI 中端到端完成:精读五到二十篇核心文献并留下可延续的理解;基于精读笔记起草 related work 且每条引用可溯源;实验有结构化记录并与稿件 claim 关联;跨越数周的多次会话中,agent 始终"记得"项目状态。
